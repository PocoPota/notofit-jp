# ブラウザは約物のカーニングをどこまで適用するか

調査日: 2026-07-28
対象: Chromium 149 / WebKit 26.5 / Firefox 151（Playwright、macOS）
関連: [../yakumono.md](../yakumono.md)、[../usage.md](../usage.md)

---

## 結論

**`kern` は「CSS の指定なしに全ブラウザで効く」とは言えなかった。** 約物の隣接処理を
`kern` に載せる判断（[../yakumono.md](../yakumono.md) の方針2）の前提が、実測で崩れた。

| エンジン | 状況 |
| -------- | ---- |
| **Chromium** | すべてのペアで効く |
| **Firefox** | 既定（`font-kerning: auto`）では**効かない**。`font-kerning: normal` を書けば全ペア効く |
| **WebKit** | **行分割が許される位置では効かない**。CSS でも強制できない |

対応は、Firefox 向けに `font-kerning: normal` を利用側に案内し、WebKit の制約は
そのまま受け入れる（→ 最後の節）。

## 測定方法

`dist/` をローカルで配信し、各エンジンで `font-size: 100px` のインライン要素を作って
`getBoundingClientRect().width / 100` を em として読む。`document.fonts.load()` で対象
文字を含む face を明示的に読み込み、`document.fonts.ready` の後に測る。

> 読み込みを待たずに測ると、フォールバックの値や `.notdef`（0.5em）を拾って
> それらしい数値が出る。実際にこれで何度か誤った結論を出した。

## 結果

`」「` は全角ベタなら 2.000em、JLREQ どおりなら 1.500em。

| ペア | Chromium | WebKit | Firefox 既定 | Firefox `font-kerning: normal` |
| ---- | -------- | ------ | ------------ | ------------------------------ |
| `」「` `』「` `）（` `】【` | 1.500 | **2.000** | 2.000 | 1.500 |
| `。」` `、」` `」』` `」・` `」：` `。、` `「『` | 1.500 | 1.500 | 2.000 | 1.500 |
| `（）`（調整対象外） | 2.000 | 2.000 | 2.000 | 2.000 |
| `AV`（欧文のカーニング） | 1.342 | 1.342 | 1.342 | 1.342 |

欧文のカーニングは3エンジンとも既定で効いている。**CJK の約物に限った挙動**である。

## WebKit の規則

失敗するのは「**2文字目が始め括弧**」の組み合わせだけ。同じ −500 を与えたペアで、
行分割の可否によって結果が割れる。

| ペア | 行分割 | WebKit |
| ---- | ------ | ------ |
| `。」` | 不可（閉じ括弧は行頭に来られない） | 1.500 |
| `。「` | **可**（始め括弧の前で切れる） | **2.000** |
| `、」` | 不可 | 1.500 |
| `、（` | **可** | **2.000** |
| `「『` | 不可（始め括弧の後では切れない） | 1.500 |
| `」「` | **可** | **2.000** |

**行分割が許される位置でシェイピングのランが切れ、GPOS が届かない**と読める。

CSS では回避できない。`white-space: nowrap` でも変わらず、`word-break: keep-all` は
むしろ全ペアで効かなくなる。GPOS はランが切れた時点で届かないため、フォント側で打てる
手は `hmtx`（字幅そのもの）しかない。

## 検討した対策と、採らなかった理由

始め括弧の左のアキを量 `B` だけ字幅に焼き込めば、シェイピングを経ずに詰まるため
WebKit でも効く。

| `B` | WebKit の `」「` | Chromium の `」「` | 単独の `あ「い` |
| --- | ---------------- | ------------------ | --------------- |
| **0（採用）** | 2.000em | 1.500em | **2.915em**（JLREQ どおり） |
| 250 | 1.750em | 1.500em | 2.665em |
| 500 | 1.500em（全エンジン一致） | 1.500em | 2.415em |

**`B = 0` を採る。** 理由は3つ。

1. **失敗する範囲が狭い。** 始め括弧の前に別の約物が来る場合だけで、`「` がかな・漢字の
   後や行頭に現れる場合はもともと調整対象外。`。」` `、」` `」・` など頻出の組み合わせは
   WebKit でも効いている
2. **WebKit での結果は全角ベタであり、誤った組版ではない。** 改善が一部届かないだけで、
   壊れるわけではない
3. **`B` を上げると、より頻度の高い「単独の始め括弧」を犠牲にする。** これは `palt` の
   一律焼き込みを不採用にしたときと同じ問題（→ [../yakumono.md](../yakumono.md)）

方針4（全エンジンで同一の結果）を部分的に諦める判断である。均一性を優先するなら
`B = 500` になるが、そのときは単独の `「` が常に半角になる。

## あわせて確認したこと

- **`halt` の削除で Chromium の `text-spacing-trim` は動かない。** `text-spacing-trim:
  space-all` を指定してもしなくても結果が変わらない（`」「` は 1.500em のまま）。
  計画書で未検証としていた項目が確認できた
- **`palt` / `halt` を CSS で指定しても字送りは変わらない。** 削除済みであることの確認
- **`text-autospace`** は3エンジンとも同じ挙動（`あA` が 1.698em → 1.823em）。ただし
  Chromium の初期値は `no-autospace` で、書かなければ効かない
- かな・全角英数のプロポーショナル化と、和欧の合成結果は3エンジンで完全に一致する
  （`あいうえお` 4.610em、`日本語とEnglish` 7.151em）
