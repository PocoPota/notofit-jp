# palt の中身はウェイトによって入れ替わる

調査日: 2026-07-27（2026-07-28 に焼き込み対象の変更を反映）
関連: 計画書 [../plan.md](../plan.md) の工程② と R3

---

## このメモの用件

Noto Sans JP の `palt` は、`wght`（太さ）の値によって中身が入れ替わる。そのせいで
**`palt` を焼き込む実装には、守らないと壊れる制約が2つある**。また、これを踏まえて
**R3（ウェイトによる字送りの段差）は現状では問題にならない**と判断した。その根拠を残す。

| | 内容 |
| --- | --- |
| 制約1 | **焼き込みは静的インスタンス化の後に行う。** 可変のまま焼くと、どのウェイトの `palt` を焼いたのか決まらない |
| 制約2 | **`palt` にぶら下がる lookup を全部たどって合計する。** 1つ目だけ見ると 700 以上で値がずれる |
| 判断 | **R3 は 400 / 700 の2ウェイトでは起きない。** 将来 500 / 600 を足したときだけ効いてくる |

実装は `notofit/palt.py`、検証は `tests/test_palt.py`（400 / 700 の両方で確認）。

## 前提となる用語

### `palt`

OpenType の feature（機能）のひとつ。**全角固定の字幅を、字面に応じた幅に詰める**もの。
名前は proportional alternate widths の略。

和文は原則すべての文字が全角（1em = 1000 ユニット）を占めるが、`palt` を有効にすると
対象の文字がそれぞれ固有の幅に変わる。詰め幅は文字ごとに違い、約物のように字面が小さい
ものほど大きく詰まる。

| 文字 | 全角時 | `palt` での変化 | 結果 |
| ---- | ------ | --------------- | ---- |
| `あ` | 1000 | −29 | 971 |
| `ア` | 1000 | −69 | 931 |
| `Ａ` | 1000 | −224 | 776 |
| `。` | 1000 | −500 | 500 |

本プロジェクトでは、この変化量の一部または全部を**フォントの既定の字幅に恒久的に
書き込む**（＝焼き込む）。CSS で `palt` を指定しなくても同じ結果が得られるようにするため。

### 対象グリフ

`palt` が変化量を持っている文字のこと。持っていない文字（漢字など）は `palt` を有効に
しても全角のまま変わらない。Noto Sans JP は **328グリフ**が対象。

| 分類 | グリフ数 |
| ---- | -------- |
| かな（ひらがな・カタカナ） | 195 |
| 全角英数 | 60 |
| 約物 | 45 |
| その他（記号など） | 28 |

### `XAdvance` と `XPlacement`

`palt` が各グリフに持つ2つの値。

- **`XAdvance`** — 字幅（次の文字までの送り量）を何ユニット変えるか
- **`XPlacement`** — 字面そのものを水平に何ユニット動かすか

`あ` の `(−29, −14)` は「幅を 29 縮め、字面を左に 14 動かす」の意味。幅だけ縮めると字面が
枠の中で右に寄ってしまうため、両方を組で扱う必要がある。

### lookup

feature の実体となる**変化量のまとまり**。「`palt` を有効にする」とは、実際には
「`palt` が指している lookup を順に適用する」ことを意味する。

feature は複数の lookup を指すことができ、**その場合は順に適用されて効果が累積する**。
このメモの本題はここにある。

### `FeatureVariations`

可変フォントの仕組みのひとつで、**軸の値（ここでは `wght`）に応じて feature が指す
lookup を差し替える**。デザイナーが「太いウェイトでは詰め方を変えたい」と指定できる。

## 何が起きているか

Noto Sans JP の `palt` が指す lookup は、`wght` によって変わる。

| wght | `palt` が指す lookup | 対象グリフ数 |
| ---- | -------------------- | ------------ |
| 400〜680 | `6` のみ | 328 |
| 700〜900 | `6` と `10` | 328 + 305（重複あり） |

**lookup 6 はどのウェイトでも同じ内容**で、これが `palt` の基本の値。lookup 10 は太い
ウェイトのときだけ加わる**補正の層**で、小さな正の値を持つ。正なので、詰めを少し戻す
（＝緩める）方向に働く。

`あ` の例:

| wght | lookup 6 | lookup 10 | 合計 | 結果の字幅 |
| ---- | -------- | --------- | ---- | ---------- |
| 400 | −29 | — | **−29** | 971 |
| 700 | −29 | +15 | **−14** | 986 |

太いウェイトのほうが 15 ユニット（1.5%）広い。字面が太くなるぶん余裕を持たせる設計と
読める。

### だから制約2が要る

lookup 6 だけを読んで焼き込むと、700 以上では lookup 10 の分（+15）が焼かれずに `palt`
の中に残る。すると**焼き込み後にさらに `palt` を有効化したとき、その残りが二重に効いて
意図しない幅になる**。`palt` が指す lookup をすべてたどって合計する必要がある。

### だから制約1が要る

`instantiateVariableFont` で特定のウェイトに固定すると、`FeatureVariations` が解決されて
lookup の構成が確定する。可変フォントのまま焼き込むと、`6` だけの状態と `6 + 10` の状態の
どちらを焼いたのかが決まらない。

## R3 をどう判断したか

本プロジェクトが `palt` を焼き込むのはかな・全角英数である（約物は全角のまま残し、隣接
処理は `kern` が担う。→ [../yakumono.md](../yakumono.md)）。この対象で 400 と 700 の値は
ほとんどが異なる（かな 197グリフ中 192、全角英数 62グリフ中 60）。

ただし**境界の内側では完全に一定**で、段差は一箇所しかない。`あいうえお` の5文字を焼き
込んだ後の字送りを測ったもの（全角のままなら 5.000em）。

| wght | `palt` が指す lookup | `あいうえお` | 前との差 |
| ---- | -------------------- | ------------ | -------- |
| 400 | `6` | 4.6100em | |
| 500 | `6` | 4.6100em | ±0 |
| 600 | `6` | 4.6100em | ±0 |
| 680 | `6` | 4.6100em | ±0 |
| 700 | `6` + `10` | 4.6650em | **+0.055** |
| 800 | `6` + `10` | 4.6650em | ±0 |
| 900 | `6` + `10` | 4.6650em | ±0 |

**段差の向きは「太い側でわずかに緩む」で、大きさは1文字あたり約 1.1%。** 計画書の R3 は
当初「太いウェイトで急に詰まる」と想定していたが、向きが逆で量も小さい。

- **400 / 700 だけを作る現状では問題にならない。** そもそも異なるウェイトであり、字送りに
  差があること自体が自然
- **効いてくるのは将来 500 / 600 を追加したとき。** 400〜600 が同一値、700 以上が同一値と
  なり、600 と 700 の間にだけ不連続が生じる。その段階で気になるなら、全ウェイトの `palt`
  のカバレッジと値を片側に揃えて解消する

## 補足: 境界の位置

`FeatureVariations` の切り替え条件は、正規化座標で 0.779〜1.0 と記録されている。可変
フォントの軸は内部的に 0〜1 に正規化されており、その 0.779 の位置が境界という意味。

`wght` の範囲は 100〜900 なので単純比例なら 100 + 0.779 × 800 = 723 になるが、**実際の
境界は 700 以下**である。Noto Sans JP は `avar` テーブルで正規化を非線形に補正しており、
比例計算では位置を読み違える。境界を知りたいときは計算ではなく、実際にインスタンス化して
lookup の構成を見るのが確実。
