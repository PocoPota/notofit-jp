# palt はウェイトの境界で切り替わる

調査日: 2026-07-27（2026-07-28 に焼き込み対象の変更を反映）
関連: 計画書 [../plan.md](../plan.md) の工程② と R3

---

## 事実

Noto Sans JP の `GPOS` には `FeatureVariations` があり、**`wght` がある値を超えると
`palt` に lookup が1つ追加される**。

| wght    | palt の lookup | 対象グリフ数 |
| ------- | -------------- | ------------ |
| 400〜680 | `[6]`          | 328          |
| 700〜900 | `[6, 10]`      | 332          |

条件は正規化座標で 0.779〜1.0。**700 はすでにこの範囲に入る**（`avar` により正規化が
非線形なため、単純比例で計算すると境界を 723 と読み違える）。本プロジェクトの対象で
ある 400 / 700 がまたいでいる。

## 焼き込み対象への影響

本プロジェクトが `palt` を焼き込むのはかな・全角英数である（約物は全角のまま残し、隣接
処理は `kern` が担う。→ [../yakumono.md](../yakumono.md)）。この対象で 400 と 700 の値は
**ほとんどが異なる**。かな 197グリフ中 192、全角英数 62グリフ中 60。

ただし**境界の内側では完全に一定**であり、段差は一箇所しかない。`あいうえお` を焼き込んだ
後の字送り。

| wght | palt lookups | `あいうえお` | 前との差 |
| ---- | ------------ | ------------ | -------- |
| 400  | `[6]`        | 4.6100em     |          |
| 500  | `[6]`        | 4.6100em     | ±0       |
| 600  | `[6]`        | 4.6100em     | ±0       |
| 680  | `[6]`        | 4.6100em     | ±0       |
| 700  | `[6, 10]`    | 4.6650em     | **+0.055** |
| 800  | `[6, 10]`    | 4.6650em     | ±0       |
| 900  | `[6, 10]`    | 4.6650em     | ±0       |

**段差の向きは「太い側でわずかに緩む」であり、大きさは1文字あたり約 1.1%。** 重いウェイト
ほど字面に余裕を持たせる設計と読める。

## R3 の評価

計画書の R3 は当初「太いウェイトで急に詰まる」と想定していたが、**向きが逆で、量も小さい**。

- **400 / 700 のみを作る現状では問題にならない。** そもそも異なるウェイトであり、字送りに
  差があること自体が自然である
- **効いてくるのは将来 500 / 600 を追加したとき。** 600 と 700 の間にだけ不連続が生じ、
  400〜600 が同一値、700 以上が同一値という2段構成になる

ウェイトを増やす段階で、必要なら全ウェイトの `palt` 値を片側に揃える（カバレッジと値を
統一する）ことで解消できる。

## 実装への反映

**`palt` の焼き込みは静的インスタンス化した後に行う。** 可変フォントのまま焼き込むと、
どのウェイトの `palt` を焼いたのかが曖昧になる。`instantiateVariableFont` を通すと
`FeatureVariations` は解決され、そのウェイトの lookup 構成が確定する。

**焼き込み処理は `palt` にぶら下がるすべての lookup を辿って合計する。** シェイピング時は
複数の lookup が累積して適用されるため、lookup 6 だけを見ると 700 以上で値がずれる。

実装は `notofit/palt.py`、検証は `tests/test_palt.py`（400 / 700 の両方で確認）。
