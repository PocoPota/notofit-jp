# 約物の処理

Notofit JP における約物（句読点・括弧類・中点類）の字送りの扱いと、その決定経緯。

かな・全角英数の字幅は [proportional.md](proportional.md)、計画書は [plan.md](plan.md)。

---

## 1. 前提: 全角ベタはすでに正しい

和文の約物は、**全角の枠に半角のインクが入り、残り半分がアキとして機能する**設計になって
いる。手元のデータで確認できる。`palt` の `XPlacement` は `「` が −481、`」` が −19
であり、`「` はインクが右半分に、`」` は左半分にある。

| 約物 | インクの位置 | 空いている側 |
| ---- | ------------ | ------------ |
| 始め括弧類 `「『（` | 右半分 | 左 |
| 終わり括弧類 `」』）` | 左半分 | 右 |
| 句点類 `。` 読点類 `、` | 左下 | 右 |
| 中点類 `・：；` | 中央 | 左右に四分ずつ |

これは JLREQ / JIS X 4051 が定める「半角字形 ＋ 二分アキ」そのものである。
**約物が単独で現れる限り、全角ベタは正しい組版である。**

問題が生じるのは**約物が隣接したとき**だけ。空いている側が向かい合うとアキが二重になる。
`」「` は「右の空き ＋ 左の空き」で全角分の隙間ができるが、JLREQ が求めるのは二分アキで
ある。

**したがって必要なのは「約物を詰めること」ではなく「隣接時に重複したアキを取り除くこと」。**

## 2. 方針

**約物の字幅は全角のまま変更せず、隣接時のアキだけを `kern` のペア調整で取り除く。**

理由は3つ。

1. **JLREQ と一致する。** 単独の約物は全角を保ち、隣接時のみ二分アキになる
2. **全ブラウザで同じ結果になる。** `kern` は `font-kerning: auto` が既定であり、CSS で
   指定しなくても効く。エンジンによる実装差もない
3. **置き換え互換性への影響が最小。** 和文の字送りが変わるのは隣接約物という限られた
   箇所だけで、単独の約物や本文の大半は Noto Sans JP と同じ字送りを保つ

## 3. 設計

`GPOS` の PairPos **Format 2（クラスベース）**で実装する。

```
クラス1: 始め括弧類    「『（〔［｛〈《【
クラス2: 終わり括弧類  」』）〕］｝〉》】
クラス3: 句点・読点類  。、．，
クラス4: 中点類        ・：；
```

後続グリフの前をどれだけ引くか（1000 upem 単位）。

| 前＼後 | 始め括弧 | 終わり括弧 | 句点・読点 | 中点 | その他 |
| ------ | -------- | ---------- | ---------- | ---- | ------ |
| 始め括弧 | −500 | 0 | 0 | 0 | 0 |
| 終わり括弧 | −500 | −500 | −500 | −500 | 0 |
| 句点・読点 | −500 | −500 | −500 | −500 | 0 |
| 中点 | −500 | 0 | 0 | 0 | 0 |
| その他 | 0 | 0 | 0 | 0 | 0 |

**「その他」（かな・漢字）との組み合わせがすべて 0 である点が要。** 約物が単独で現れる
限り字送りは一切変わらない。

**引く量はどの組み合わせでも −500 になる。** 全角ベタでは空いている側が向かい合って
二分ぶん余計にアキができるため、それを取り除けば JLREQ の目標値に届く。目標とするアキが
組み合わせによって違っても、引く量は同じである点に注意。

| 組み合わせ | 引いた後の字面のアキ | JLREQ の規定 |
| ---------- | -------------------- | ------------ |
| `」「` `。」` | 二分アキ | 連続する括弧・句読点 |
| `「『` | ベタ | 連続する始め括弧 |
| `」・` `・「` | 四分アキ | 中点類の前後 |

たとえば `」・` は、`」` のインクが左半分、`・` が中央で左右に四分の空きを持つため、
−500 を引いてはじめて字面のアキが四分になる。−250 では二分アキのままで規定に届かない。

実装では2つの値に分けている（`pair` と `middle`、既定はどちらも −500）。行列の構造は
JLREQ から導かれるものとして固定し、中点まわりだけ緩めたい場合に触れるようにするため。

数百グリフを4クラスに畳めるためデータ量は小さく、グリフの書き換えも不要。実装は
`fontTools.otlLib.builder.buildPairPosClassesSubtable`。Noto Sans JP の既存の `kern` には
約物のペアが入っていない（`」「` が既定 2.000em のまま）ため、衝突しない。

行列の値は調整の余地があるため、設定から変えられる形にする。

## 4. 併せて行う処理

### `palt` と `halt` の削除

Noto Sans JP は `halt` を持ち、`text-spacing-trim` の既定値は `normal` であるため、
**Chromium では指定なしでもすでに文脈依存のトリムが効いている**。`halt` を残したまま
`kern` を追加すると、Chromium だけ二重適用になる。

`halt` を削除すれば `text-spacing-trim` が無効化され、3エンジンとも `kern` による同一の
結果に揃う。縦組み用の `vhal` / `vpal` / `vkrn` は横書き限定の方針により不要であり、
`halt` だけ消して残すのは中途半端なため、まとめて削除する。

**`palt` も同じ理由で削除する。** 約物には焼き込まないため値が残っており、CSS で
`palt` を指定されると半角化と `kern` の調整が二重にかかる。実測では `」「` が 1.500em
から **0.500em** まで潰れた。`halt` とまったく同じ構図であり、片方だけ残す理由がない。

約物の字幅を決めるのはフォントの側である、という立場を取る以上、CSS から上書きできる
余地は残さない。「約物半角」を CSS で呼び出せる余地は失われるが、それは `ss09` 案を
不採用にした判断（→ 5）と一貫している。

#### Chromium の既定動作との一致

ブラウザ上での実測（`」「` の幅）。

| | Notofit JP | 素の Noto Sans JP |
| --- | ---------- | ----------------- |
| Chromium | **1.500em** | 1.500em（`text-spacing-trim` が既定で効く） |
| Safari / Firefox | **1.500em** | 2.000em（全角ベタ） |

**Chromium が既定で行っている組版を、`kern` によって全ブラウザで再現できている。**
本方式が妥当であることの裏づけになる。

なお調整ツールで素の Noto を比較表示する際は、この既定のトリムを `text-spacing-trim:
space-all` で無効化しないと、比較対象がすでにトリム済みで差が見えない。

#### 根拠と、その確度

`halt` / `chws` を持たないフォントで無効化される、という挙動の出典は MDN である。

> **Note:** To avoid the risk of excessive kerning, fonts must have the OpenType Alternate
> Half Widths (`halt`) feature, the Contextual Half-width Spacing (`chws`) feature, or both.
> If the font doesn't have either feature, `text-spacing-trim` is disabled.
> — [MDN, Description 節](https://developer.mozilla.org/en-US/docs/Web/CSS/text-spacing-trim)

**これは仕様の要件ではなく、Chromium の現行実装の挙動である。**

- [CSS Text Module Level 4 §8.5](https://www.w3.org/TR/css-text-4/#text-spacing-trim-property)
  には該当する記述を確認できていない（§8.5 の全文を取得できていないため、断定はしない）
- [csswg-drafts #8293](https://github.com/w3c/csswg-drafts/issues/8293) が 2023年1月から
  未解決のまま。提案は3段構えで、①隣接トリムは `chws` / `vchw` に従う ②その他は `halt` /
  `vhal` を使う ③**これらを持たないフォントでは UA が合成してもよい**

③の方向で決着すると、将来は `halt` がなくてもトリムが適用されうる。したがって
「`halt` を削除すれば無効化される」は現時点の Chromium に依存する前提である。

ただし **`kern` 方式はこの不確実性に対して頑健**であり、方式選択の補強材料になる。

| 方式 | 将来 UA がトリムを上乗せした場合の `」「` |
| ---- | ------------------------------------------ |
| `palt` 一律焼き込み ＋ `halt` 残置 | **0.000em**（約物が潰れる） |
| 約物は全角のまま ＋ `kern` ペア調整 | 1.500em → 1.000em 程度（詰まりすぎるが読める） |

焼き込み方式では破綻するのに対し、`kern` 方式は劣化が緩やかで済む。

### かな・全角英数は別扱い

`palt` の対象は約物だけではなく、かな（195グリフ）・全角英数（60）も含む。これらは約物と
切り離して扱う。前後の文字によらず一定の幅で構わないため、本章のような文脈依存の処理は
要らない。

**プロポーショナル化するかどうかは M2 で決める**（既定はする側）。詳細は
[proportional.md](proportional.md)。

## 5. 検討して不採用とした案

### `chws` を実装する

`chws` は隣接約物のトリムを行う feature だが、**実装しているのは Chromium 系のみ**。
3エンジンでの実測でも WebKit / Gecko では効かなかった。仕様は「エンジンが JLREQ 相当を
実装していないなら既定で有効にすべき」としているが、両者は該当条件でありながら未実装。

### `text-spacing-trim` に委ねる

Chromium では既定で効いており、`」「` を JLREQ どおり 1.5em にする。しかし MDN の
ステータスは Limited availability（Baseline 未達）で、他エンジンでは全角ベタのまま。
**ブラウザ間で結果が割れる**ため、方針4（フォント側に焼き込み、ブラウザ実装差の影響を
受けない）に反する。

サイト側で吸収する道もない。CSS には「約物が隣接したとき」を選択する手段がなく、JS で
テキストノードを走査する方法は動的コンテンツに弱い。

### `palt` を約物にも一律で焼き込む

当初の案。比率 `f` の分を `hmtx` に焼き込み、既定状態を全角ベタと `palt` 全開の中間に
固定する。実測値は以下のとおり。

| `f` | `」「`（隣接） | `あ「い`（単独） |
| --- | -------------- | ---------------- |
| 0.0 | 2.000em | 3.000em |
| 0.34 | 1.660em | 2.801em |
| 0.5 | **1.500em** | 2.708em |
| 1.0 | 1.000em | 2.415em |
| JLREQ | 1.500em | 3.000em |

`f = 0.5` で隣接時は JLREQ と一致するが、**`palt` は文脈を見ないため単独の約物まで
詰まる**。単独時 2.7em は JLREQ の 3.0em より詰まりすぎで、これは比率をどう選んでも
避けられない。`kern` なら両方を同時に満たせるため不採用とした。

### `palt` 焼き込み ＋ `halt` 再合成

焼き込みに合わせて `halt` を再スケールし、Chromium では `text-spacing-trim` による文脈
処理も効くようにする案。整合性は保てるが、**文脈処理が効くのは Chromium だけ**という
状態は変わらず、ブラウザ間で結果が割れる。

なお、焼き込んだうえで `halt` を放置すると破綻する。実測（`」「` に `halt` を適用）:

| `f` | 既定 | `halt` 適用後 |
| --- | ---- | ------------- |
| 0.0 | 2.000em | 1.000em |
| 0.34 | 1.660em | **0.660em** |
| 1.0 | 1.000em | **0.000em** |

`f = 1.0` では約物が完全に潰れる。`halt` を削除する判断はこの実測に基づく。

### 残りを `ss09` などの stylistic set に逃がす

一部だけ焼き込み、残りを任意の feature として保持する案。CSS で指定したページだけ詰まる
ことになり、**指定の有無で見た目が変わる**。方針4に反するため不採用。

## 6. 限界

**行頭・行末の処理はできない。** 「行頭の始め括弧を半角にする」はペアの情報では決まらず、
行の中での位置を知る必要がある。`text-spacing-trim` にしかできない領域であり、頻度が
低いため妥協する。JLREQ でも「行頭全角」「行頭半角」の両方が許容される範囲である。

**3つ以上連続すると累積する。** `。」「` はペアが2つ成立し、それぞれ独立に適用される。
JLREQ には連続時の別規則があるがペアでは表現できない。多少詰まりすぎる程度で破綻はしない。

**約物を1つのスライスに集める必要がある。** ブラウザは**フォントをまたいでカーニングを
適用しない**。配信はスライス方式で、Google Fonts の区切りでは約物が11個のスライスに
分散するため、そのままでは `。」` `』「` `」・` のように**別スライスに落ちた組み合わせで
調整が効かない**（実測で 2.000em のまま）。

そこで工程⑤で、`kern` の対象となる約物31字を1つのスライスに集め、他のスライスからは
取り除く。これにより全ての組み合わせが同一フォント内に収まる。Google の区切りをそのまま
使うという方針7からの逸脱だが、対象は31字・4KB弱で、頻度に基づく区切りの意図は保たれる。

**`font-kerning: none` で無効化される。** サイト側がこれを指定していると効かない。
`hmtx` への焼き込みが絶対に覆らないのに対し、`kern` は feature である以上わずかに逃げ道が
残る。稀なケースだが、方針4を完全には満たさない点として記録しておく。
